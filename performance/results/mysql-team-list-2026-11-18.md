# 팀 모집 목록 MySQL 성능 재측정

로컬 H2에서 팀 목록의 SQL 횟수는 줄었지만 p95는 증가했습니다. MySQL에서도 쿼리 감소가 재현되는지 확인하고, 동일한 데이터에서 응답 시간과 처리량을 다시 측정했습니다.

## 비교 조건

- 측정일 2026-11-18, 대상 `GET /api/teams?competitionId=1&page=0&size=10`
- 변경 전 `38964e8`, 변경 후 `c8288d2`
- macOS arm64, Java 21.0.10, MySQL 8.4.13, k6 2.4.0
- 두 빌드가 루프백에서 같은 전용 DB를 사용했습니다. 데이터는 한 번만 생성했고, 각 JVM에는 같은 힙 크기(`-Xms256m -Xmx512m`)를 적용했습니다. API 요청 처리와 무관한 추출·푸시 작업자는 비활성화했습니다.
- 테스트 데이터는 팀 1,000개, 팀원 5,000명, 지원 20,000건, 채팅방 100개, 메시지 100,000건입니다.
- k6는 최대 10 VU로 22초씩 실행했습니다. 5초 증가, 15초 유지, 2초 감소 조건으로 이전 → 이후 → 이후 → 이전 → 이전 → 이후 순서로 실행했습니다.

## 내부 조회 검증

각 버전에서 요청 1건을 보내기 직전과 직후에 MySQL Performance Schema의 앱 DB 계정 SELECT 집계를 읽었습니다. 인증을 포함한 HTTP 요청 전체가 측정 범위입니다. H2의 서비스 단독 측정은 서로 다른 범위입니다.

| 지표 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 요청당 SELECT (3회 반복) | 15, 15, 15 | 6, 6, 6 |
| HTTP 응답의 JSON 본문 | 변경 후와 동일 | 변경 전과 동일 |

## 해석

팀원 수 일괄 집계로 요청당 SELECT가 9회(60%) 줄었고, 두 버전의 응답 본문은 같았습니다. k6에서는 비교 회차별 p95 차이의 방향이 바뀌었으며, 각 버전 모두 뒤 회차로 갈수록 응답이 빨라졌습니다. 버전별 중앙값에도 이 편차가 반영되므로, 이번 실행만으로 코드 변경이 응답 시간에 미친 효과를 확정하기 어렵습니다.

지연 시간을 다시 비교할 때는 측정용 요청과 별도로 충분히 예열하고, 애플리케이션과 부하 발생기를 분리한 환경에서 반복 측정합니다. 이번 기록의 범위는 팀 모집 목록입니다.
