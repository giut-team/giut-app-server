# 공모전 API 단계별 부하 테스트 (2026-11-19, 로컬 MySQL)

## 결론

- 동시 사용자 **50명에서 처리량이 초당 약 60건으로 막힌다**. 100명, 200명으로 늘려도 처리량은 그대로이고 응답 시간만 늘어난다(p95 0.9초 → 2.2초 → 5.2초). 실패는 0건이다.
- 막히는 곳은 **MySQL CPU**다. 50명 구간에서 mysqld가 CPU 약 9코어(900%)를 쓰고 맥 전체 유휴율이 0%였다. Spring은 약 30%였다.
- DB 시간의 **약 68%가 목록 API의 `COUNT` 쿼리**다. `Page`가 요청마다 공개·마감 전 공모전 약 4만 7천 행을 센다.
- 나머지 대부분(약 30%)은 **인덱스를 못 타고 매번 정렬(filesort)하는 목록 쿼리 3종**이다: 마감 임박 순, 조회수 순, 카테고리+마감 임박 순.
- Top5(메모리 캐시)·상세처럼 가벼운 API도 1초 넘게 걸린 건 자체 비용이 아니라 **커넥션 풀(10개) 대기** 때문이다. 스레드 덤프에서 요청 스레드 약 30개가 `HikariPool.getConnection`에서 기다리고 있었다.

## 환경과 데이터

- 서버: `689ce31`(refactor/competition) bootJar, `perf` 프로필, JVM 1GB, HikariCP 기본값(최대 10), Tomcat 기본값.
- DB: MySQL 26.7.0(Homebrew, 로컬 폐기 인스턴스, buffer pool 1GB). 운영 RDS 8.4와 버전·하드웨어가 다르다.
- 서버·MySQL·k6가 한 맥(10코어)에서 같이 돌아 CPU를 나눠 쓴다. 절대 수치보다 병목 위치와 상대 비교로 본다.
- 데이터: 사용자 5,004명(테스트 사용자 5,000명 학교 인증 완료), 공모전 50,001건(공개·마감 전 45,001건, 7일 이내 마감 2,609건), 스크랩 549,948건(인기 공모전 쏠림, 최대 3,593건).
- 주의(2026-11-22 추가): 당시 시드에는 문자셋 지정이 없었다. `mysql` 클라이언트가 latin1로 접속했다면 한글이 이중 인코딩돼, 한글 검색어 요청이 아무것도 찾지 못하고 전체 행을 훑었을 수 있다. 11-22에 같은 시드에서 이 현상을 확인하고 시드에 `SET NAMES utf8mb4`를 넣었다. 이 측정의 데이터는 남아 있지 않아 실제로 그랬는지는 확인하지 못했다.

## 병목 진단

### 50명 구간 자원 사용 (별도 45초 재측정, 처리량 60.2 req/s로 재현)

| 항목 | 값 |
|---|---|
| mysqld CPU | 885~910% |
| Spring(java) CPU | 25~45% |
| 맥 전체 | user 91.8%, sys 8.2%, idle 0% |
| MySQL `Threads_running` | 11~12 (커넥션 풀 10개가 모두 쿼리 실행 중) |
| 요청 스레드(스레드 덤프 2회) | 커넥션 풀 대기 27~31개, DB 응답 대기 9~10개 |

### DB 시간 상위 쿼리 (`performance_schema`, 테스트 전체 누적)

| 누적 시간 | 비중 | 쿼리 | 평균(부하 중) | 읽은 행 |
|---:|---:|---|---:|---:|
| 1,703s | 51% | 목록 `COUNT` (필터 없음) | 151ms | 47,505 |
| 403s | 12% | 목록 `ORDER BY application_end_at, id DESC` (마감 임박 순) | 177ms | 47,570 |
| 320s | 10% | 목록 `ORDER BY view_count DESC, id DESC` (조회수 순) | 179ms | 47,574 |
| 300s | 9% | 목록 `COUNT` + 검색어 `LIKE` | 166ms | 47,501 |
| 280s | 8% | 목록 카테고리 + 마감 임박 순 | 170ms | 47,595 |
| 257s | 8% | 목록 `COUNT` + 카테고리 | 156ms | 47,501 |

`COUNT` 쿼리 합계는 전체 DB 시간 약 3,354초 중 약 2,277초(약 68%)다.

### 부하 없을 때 단건 비용 (`EXPLAIN ANALYZE`)

| 쿼리 | 시간 |
|---|---:|
| 목록 `COUNT` | 26.7ms |
| 최신 순 페이지 (`ORDER BY id DESC`, 인덱스 역순) | 0.03ms |
| 마감 임박 순 페이지 | 40.6ms |
| 조회수 순 페이지 | 40.5ms |
| 검색어 `COUNT` | 29.3ms |

- 마감 임박 순은 `idx_competitions_status_app_end_at` 인덱스가 있어도 `application_end_at ASC, id DESC`처럼 **정렬 방향이 섞여 있어** 인덱스 순서를 쓰지 못하고 4만 5천 행을 정렬한다(실행 계획: `Sort: c.application_end_at, c.id DESC`).
- 스크랩 순(`scrap_count DESC, id DESC`)은 방향이 같아 인덱스 역순 스캔으로 처리된다.
- 조회수 순은 인덱스가 없다(코드 주석에 적힌 알려진 한계).

## 개선 후보 (미적용, 효과는 예상)

1. **목록 `COUNT` 제거 또는 줄이기**: 앱이 전체 개수·전체 페이지 수를 쓰지 않고 다음 페이지 여부만 쓴다면 `Slice`로 바꿔 `COUNT`를 없앤다. 전체 개수가 필요하면 필터 조합별로 짧게(예: 30초~1분) 캐시한다. DB 시간의 약 68%가 대상이다.
2. **마감 임박 순 정렬 방향 맞추기**: 동률 정렬을 `id ASC`로 바꾸거나 `(publication_status, application_end_at, id DESC)` 인덱스를 만든다. 카테고리 필터용으로는 `(publication_status, category, application_end_at)`도 검토한다.
3. **조회수 순 인덱스**: `(publication_status, view_count)`. 다만 상세 조회마다 `view_count`가 바뀌어 인덱스 갱신 비용이 생기므로, 조회수 순 사용 빈도를 보고 정한다.
4. 커넥션 풀을 늘리는 건 지금은 효과가 없을 것으로 예상한다. MySQL CPU가 이미 포화라 동시 쿼리만 늘어난다.

## 다시 실행하기

1. 폐기용 MySQL에 시드를 넣고(공모전·스크랩·사용자), `perf` 프로필로 서버를 띄운다. 테스트 사용자는 `role=STUDENT`, `status=ACTIVE`, `token_version=0`, `university_verified_at` 값이 있어야 한다.
2. 서버와 같은 `JWT_SECRET`으로 실행한다.

```bash
JWT_SECRET=<서버와 같은 값> k6 run performance/k6/competition-load.js
```

- 사용자·공모전 id 범위: `USER_ID_MIN/MAX`, `COMPETITION_ID_MIN/MAX`(기본 5~5004, 2~50001).
- 단계·시간: `LEVELS=10,50,100,200`, `RAMP_SECONDS=30`, `STAGE_HOLD_SECONDS=60`, `THINK_MAX_SECONDS=0.5`.
- 결과 파일: `RESULT_PATH`(기본 `build/reports/performance/k6-competition-load.md`).
