# 공모전 목록 전체 개수 캐시 전후 부하 테스트 (2026-11-22, 로컬 MySQL)

## 결론

- 공개 목록의 전체 개수(`COUNT`)를 필터 조합별로 1분 캐시하자 **한계 처리량이 초당 약 30~40건에서 약 70~86건으로 약 2.2배** 늘었다. 같은 6분 30초 동안 처리한 요청 수도 약 1만 1천~1만 2천 건에서 약 2만 4천~2만 6천 건으로 늘었다. 실패는 0건이다.
- 동시 사용자 50명 구간의 p95가 **1.7~2.4초에서 0.9~1.1초로**, 200명 구간의 p95가 **9.7~10.1초에서 3.5~4.5초로** 줄었다.
- DB 시간에서 `COUNT` 쿼리 비중이 **약 61%에서 약 11%로** 줄었다. 필터 없는 `COUNT`는 6분 30초 동안 약 6,200회(1,414초)에서 7회(1.1초)로 줄었다. 1분 TTL마다 한 번씩만 센 것이다.
- 남은 DB 시간의 대부분은 **인덱스를 못 타고 매번 4만 7천 행을 정렬하는 목록 조회**다: 마감 임박 순, 조회수 순, 카테고리+마감 임박 순, 검색어 목록. [이전 측정](mysql-competition-load-2026-11-19.md)의 개선 후보 2·3번이 다음 병목이다.

## 비교 대상

- 변경 전: `99a4dc0`(dev, `Page`로 요청마다 `COUNT`)
- 변경 후: `6ba6e7c`(feature/competition-list-count-cache)
  - 목록은 `Slice`로 `size + 1`건만 읽는다.
  - 전체 개수는 Caffeine 캐시(검색어 없는 필터 조합, TTL 1분)에서 가져온다. 검색어 조건은 매번 센다.
  - 마지막 페이지는 읽은 결과로 개수를 정해 세지 않는다.

## 환경과 데이터

- 서버: 각 커밋의 bootJar, `perf` 프로필, JVM 1GB, HikariCP 기본값(최대 10), Tomcat 기본값. AI 추출·푸시 워커는 껐다.
- DB: MySQL 26.7.0(Homebrew, 로컬 폐기 인스턴스, buffer pool 1GB, `performance_schema` 켬). 운영 RDS 8.4와 버전·하드웨어가 다르다.
- 서버·MySQL·k6가 한 맥(10코어)에서 같이 돌아 CPU를 나눠 쓴다. 절대 수치보다 같은 날 같은 조건의 상대 비교로 본다.
- 이날 변경 전 처리량(초당 약 30~40건)은 11-19 측정(약 60건)보다 낮다. 맥의 다른 부하 등 환경 차이로 보이며 원인은 확인하지 않았다. 그래서 11-19 수치와는 직접 비교하지 않는다.
- 데이터: `performance/k6/seed-competitions.sql` 그대로.
  - 사용자 5,000명(학교 인증 완료 STUDENT)
  - 공모전 50,000건(공개·마감 전 45,000건, 7일 이내 마감 2,609건)
  - 스크랩 639,477건(최대 4,156건)

## 부하 조건

- 스크립트: `performance/k6/competition-load.js`(변경 없음). `USER_ID_MIN=1`, `USER_ID_MAX=5000`, `COMPETITION_ID_MIN=1`, `COMPETITION_ID_MAX=50000`.
- 동시 사용자 10 → 50 → 100 → 200명, 단계마다 증가 30초 + 유지 60초. 요청 사이 0~0.5초 무작위 대기.
- 요청 비중은 11-19와 같다(목록 최신 25%, 마감 10%, 조회수 8%, 스크랩 7%, 검색 8%, 카테고리 7%, Top5 12%, 마감 임박 8%, 상세 10%, 스크랩 추가 3%, 취소 2%).
- 순서 영향을 줄이려고 변경 전 → 변경 후 → 변경 전 → 변경 후로 2회씩 돌렸다. 회차마다 서버를 새로 띄우고 `performance_schema` 집계를 비웠다.

## 확인한 것과 하지 않은 것

- MySQL 정렬 벤치마크(`GIUT_PERF_MYSQL_TEST=true`, `CompetitionSortMySqlBenchmarkTest`)가 변경 후 코드로 통과했다(2개, 건너뜀 0). `Slice` 조회의 정렬이 MySQL에서 그대로 동작한다. 이 테스트는 테스트 설정상 개수 캐시를 끈 상태다.
- 하지 않은 것: CPU·스레드 덤프 재측정, 운영과 같은 사양에서의 측정. 운영 수치는 이 결과와 다를 수 있다.

## 다시 실행하기

1. 폐기용 MySQL에 빈 DB를 만들고, 서버를 한 번 띄워 스키마를 만든 뒤 내린다.
2. `performance/k6/seed-competitions.sql`을 넣는다.
3. 비교할 커밋마다 bootJar를 만들어 `perf` 프로필로 띄우고 같은 `JWT_SECRET`으로 k6를 돌린다.

```bash
JWT_SECRET=<서버와 같은 값> USER_ID_MIN=1 USER_ID_MAX=5000 COMPETITION_ID_MIN=1 COMPETITION_ID_MAX=50000 \
  k6 run performance/k6/competition-load.js
```

4. 회차마다 `TRUNCATE performance_schema.events_statements_summary_by_digest`로 집계를 비우고, 끝나면 `SUM_TIMER_WAIT` 순으로 상위 쿼리를 본다.
