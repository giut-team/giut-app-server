# 공모전 목록 정렬 인덱스 전후 부하 테스트 (2026-11-22, 로컬 MySQL)

## 결론

- 마감 임박 순·카테고리+마감 임박 순·조회수 순에 정렬 순서대로 읽는 인덱스 3개를 추가하자 **한계 처리량이 초당 약 130~139건에서 약 450~485건으로 약 3.5배** 늘었다. 같은 6분 30초 동안 처리한 요청 수는 약 4만 1천 건에서 약 9만 7천~10만 1천 건으로 늘었다. 실패는 0건이다.
- 동시 사용자 200명 구간의 p95가 **1.9~2.2초에서 0.37~0.41초로**, 50명 구간의 p95가 **약 336ms에서 46~52ms로** 줄었다.
- 세 정렬 쿼리는 실행 계획에서 매번 4만 7천 행을 정렬하던 것(`Sort:`)이 인덱스 범위 스캔으로 바뀌었다. 첫 페이지 실행 시간이 약 54~60ms에서 0.04ms 이하로 줄었다.
- 남은 DB 시간의 약 83%는 **검색어 목록의 전체 개수(`COUNT`)**다. `%검색어%`는 일반 인덱스를 못 타서 요청마다 4만 7천 행을 읽는다(호출당 약 117~128ms). 이제 검색어 목록(p95 약 0.43~0.47초)이 가장 느린 API다.

## 비교 대상

- 변경 전: `6ba6e7c`(목록 개수 캐시까지 적용, 정렬 인덱스 없음)
- 변경 후: 이 문서와 같은 커밋. `Competition` 엔티티 인덱스 정의와 수동 마이그레이션 `V35__add_competition_list_sort_indexes.sql`.

| 인덱스 | 쓰는 쿼리 |
|---|---|
| `idx_competitions_status_app_end_at_id (publication_status, application_end_at, id DESC)` | 마감 임박 순, 마감 임박 목록 |
| `idx_competitions_status_category_app_end_at_id (publication_status, category, application_end_at, id DESC)` | 카테고리 + 마감 임박 순 |
| `idx_competitions_status_view_count (publication_status, view_count)` | 조회수 순(역순으로 읽어 `view_count DESC, id DESC`) |

마감 임박 순은 `application_end_at ASC, id DESC`처럼 정렬 방향이 섞여 있다. 그래서 동률 정렬을 바꾸지 않고(API 설명의 "동률이면 최근 등록 순" 유지) `id DESC`까지 넣은 내림차순 인덱스를 만들었다. Hibernate가 MySQL에 `id D`(내림차순)로 만드는 것도 빈 DB에서 확인했다.

## 환경과 데이터

- 서버·DB·부하 조건은 [목록 개수 캐시 측정](mysql-competition-list-count-cache-2026-11-22.md)과 같다(`perf` 프로필, JVM 1GB, HikariCP 최대 10, MySQL 26.7.0 로컬 폐기 인스턴스, 한 맥에서 서버·MySQL·k6 동시 실행).
- 데이터: `performance/k6/seed-competitions.sql`. 사용자 5,000명, 공모전 50,000건(공개·마감 전 45,000건), 스크랩 639,477건.
- **시드를 고친 뒤 다시 넣었다.** 이전에는 `mysql` 클라이언트가 latin1로 접속해 한글이 이중 인코딩돼 저장됐다("아"가 `EC9584`가 아니라 `C3ACE280A2`). 그래서 k6 검색어 8개 중 한글 7개가 아무것도 찾지 못하고 매번 전체 행을 훑었다. 시드 맨 앞에 `SET NAMES utf8mb4`를 넣어 고쳤다.
- 같은 이유로 이번 변경 전 처리량(약 130건)은 개수 캐시 측정의 변경 후 처리량(약 70~86건)보다 높다. 검색어 목록이 빨라졌기 때문이다. 두 문서의 절대 수치는 직접 비교하지 않는다.
- 변경 전·후를 번갈아 2회씩(전 → 후 → 전 → 후) 돌렸다. 변경 전 회차는 세 인덱스를 지웠고, 변경 후 회차는 V35를 그대로 적용한 뒤 새 jar로 띄웠다. 예전 인덱스 `idx_competitions_status_app_end_at`는 모든 회차에 있었다(운영에서 V35의 4)를 실행하기 전과 같은 상태).

## 확인한 것과 하지 않은 것

- MySQL 정렬 벤치마크(`GIUT_PERF_MYSQL_TEST=true`, `CompetitionSortMySqlBenchmarkTest`)가 새 인덱스로 통과했다(2개, 건너뜀 0). 서비스 호출 중앙값은 DEADLINE 32.9 → 17.4ms, VIEWS 23.7 → 9.3ms였다. 다만 이 벤치마크는 실행마다 ±30%쯤 흔들린다.
- 하지 않은 것: CPU·스레드 덤프 재측정, 운영과 같은 사양에서의 측정, 운영 데이터 분포에서의 실행 계획 확인.

## 다음 후보 (미적용, 효과는 예상)

1. **검색어 목록 `COUNT`**: `%검색어%`는 B-tree 인덱스로 못 줄인다. 선택지는 (가) MySQL `FULLTEXT` + ngram 파서로 검색 방식을 바꾸기, (나) 검색어 개수도 짧게 캐시하기(경우의 수가 많아 적중률은 낮다), (다) 검색 결과에서는 전체 개수를 보여주지 않고 `hasNext`만 쓰기다. 제품 결정이 필요하다.
2. 결과가 거의 없는 검색어는 목록 조회도 끝까지 훑는다(직접 실행 시 약 66ms). 1번을 고르면 함께 해결된다.
